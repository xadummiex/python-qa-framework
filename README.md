# QA Automation Framework

Монорепозиторий с автотестами. Каждый проект в `projects/` — самостоятельный
фреймворк со своей архитектурой, фикстурами и тестами.

## Проекты

| Проект | Что тестируем | Тип | Стек |
|---|---|---|---|
| [`bank_api`](projects/bank_api) | REST API банковского сервиса | API + БД | pytest · requests · pydantic · SQLAlchemy · Allure |
| [`saucedemo`](projects/saucedemo) | [saucedemo.com](https://www.saucedemo.com) | UI | pytest · Playwright · Allure |

## Структура

```
projects/
├── bank_api/          # API-фреймворк
│   ├── api/           # HTTP-клиенты и эндпоинты
│   ├── models/        # pydantic-модели запросов и ответов
│   ├── steps/         # бизнес-шаги поверх клиентов
│   ├── fixtures/      # предусловия: сессии, данные, БД
│   ├── db/            # слой SQLAlchemy для сверки с базой
│   ├── generators/    # генерация валидных тестовых данных
│   ├── scripts/       # обслуживание тестового стенда
│   └── tests/
└── saucedemo/         # UI-фреймворк
    ├── pages/         # Page Object
    ├── steps/         # Step Object поверх страниц
    ├── utils/         # константы, тестовые данные
    └── tests/
```

## API-фреймворк

Слои: тест → шаги → HTTP-клиент → эндпоинт и модели.

- **`api/`** — HTTP-клиенты. `Endpoint` хранит URL и модели запроса/ответа, клиент
  подставляет их сам и не знает конкретных ресурсов. Два уровня: `CrudRequester`
  отдаёт сырой `Response` для негативных проверок, `CrudRequesterValidate` —
  провалидированную модель для позитивных.
- **`models/`** — pydantic-модели запросов и ответов. Разбор ответа моделью
  проверяет контракт: изменение типа или пропажа поля роняет тест.
- **`checks.py`** — ожидаемый HTTP-статус передаётся в клиент функцией, поэтому
  позитивный и негативный сценарии обслуживает один и тот же шаг.
- **`steps/`** — бизнес-шаги. `ApiManager` собирает их в одну точку входа, ведёт
  реестр созданных объектов и в `cleanup()` удаляет их в обратном порядке.
- **`generators/`** — генерация данных по аннотациям модели: правила валидности
  заданы регулярками в полях, тест перекрывает только проверяемое поле.
- **`db/`** — SQLAlchemy. Тесты сверяют ответ API с фактической записью
  в PostgreSQL.
- **`fixtures/`** — предусловия: сессии, тестовые данные, сессия БД.

Тело запроса и ответа прикрепляются к Allure на уровне клиента, тесты
логирования не содержат.

## UI-фреймворк

Слои: тест → шаги → страницы.

- **`pages/`** — Page Object: локаторы и действия со страницей.
- **`steps/`** — Step Object: бизнес-шаги с проверкой результата, обёрнуты
  в `allure.step`, возвращают `self` — шаги складываются в цепочки.
- **`tests/`** — сценарии. Обращаются только к Step Object, локаторов не содержат.
- **`utils/`** — константы: URL и учётные записи.

Проверки построены на автоожиданиях Playwright, явных пауз нет. Предусловия
вынесены в фикстуры, каждый тест получает свежий контекст браузера.

## Репозиторий

- Проекты изолированы: свои фикстуры и свой `conftest.py`. Прогон UI не поднимает
  сессии и подключение к БД банка.
- `pythonpath = projects` в `pytest.ini` — импорты внутри проектов не зависят от
  расположения проекта в дереве.
- `.env` лежит рядом с конфигом своего проекта и в гит не попадает,
  в репозитории — только `.env.example`.
- Маркеры: `api` и `ui` разводят проекты, внутри банка — `account`, `credit`,
  `admin`, `auth`.
